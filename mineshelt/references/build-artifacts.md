# Build-ready authored deliverables

The goal is a completed, verified build **when construction tools exist**. If tools do not exist, deliver an honest, detailed authored plan that another builder or coding agent can execute without improvising the architectural intent.

## Required project manifest

For any substantive structure, record:
- project, Minecraft edition/version and installed relevant mods, if known;
- structure ID and purpose;
- world/dimension or resource path;
- local origin, +X/+Z/+Y orientation and compass translation;
- external dimensions, maximum height, ground datum and safety margin;
- terrain edits and protected boundaries;
- source of block IDs, required state orientations, substitutes if specifically allowed;
- placement/build mode and test method;
- what was executed and what remains merely designed.

**Coordinate ambiguity is a bug.** For example, “front faces south; local +Z goes to the public path; floor level = Y64; footprint x=0..18 and z=0..16 inclusive.” State whether sizes include eaves, porches or landscape.

## Concept packet

At least:
1. One-sentence identity and usage.
2. Site and route description.
3. Program list (rooms, levels, circulation, outside work areas).
4. Primary, secondary and focal masses.
5. Main roof profile and intersection rule.
6. Role-based material palette.
7. Main elevation/section decisions.
8. Lighting and detail concentrations.
9. Construction phases.
10. Acceptance criteria and remaining uncertainties.

Do not confuse this compact packet with a completed structure asset.

## Build passes / construction record

Use ordered passes that let an agent review the structure:
- PASS 0: world/protection backups and marking.
- PASS 1: grading, plinth and foundation.
- PASS 2: frame, floors and load path.
- PASS 3: roof and chimney/towers.
- PASS 4: openings and facade rhythm.
- PASS 5: circulation, interior and gameplay.
- PASS 6: site, paths, utilities, landscaping.
- PASS 7: screenshots, fixes and regression check.

Mark which passes were **actually executed**. Do not add a checklist of “done” merely because the code was written.

## Evidence

Appropriate evidence varies:
- Live world: dimension, coordinates, exact region, undo/snapshot method, screenshots and results of movement/interaction.
- Mod repo: path(s) changed, compatible version, build/test command + result, client placement/import check, evidence of visual revisions.
- Authored asset: actual file path, format, source version, dimensions, import/rotation test.
- Plan only: footprint, axis, elevations, materials, specific placement decisions and unsupported verification items.

Include a “Known limitations” section when anything essential is unverified.

## Reporting format

Use concise headings:
- **Intent** — what makes this structure specifically its own.
- **Realized** — exact build/file outcome, not future tense.
- **Visual revision** — defect observed, architectural change, result.
- **Validation** — actual tests/screenshots with honest status.
- **Remaining** — concrete open issues or explicit none *within checked scope*.

Never claim “finished” if only a brief or a theoretical plan was produced.
